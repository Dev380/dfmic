## Project memory

- **RT while developing:** use `tools/dfmic-rt` (sudo + `setpriv` ambient caps). `sudo -E` and `setcap` both fail because setuid/capability files put glibc in secure-execution mode, which drops `LD_LIBRARY_PATH` — and Slint's winit backend `dlopen`s libwayland/libEGL through it ("The wayland library could not be loaded").
- **GUI renderer:** femtovg (default, hardware GL) repaints the whole window every frame at ~2.2 ms CPU/frame for this UI. That cost is *area-independent* (2.5 ms even at 200×200): it is scene traversal, glyph-run iteration and path tessellation, not rasterisation. Slint's software renderer is 3.5× cheaper only when GL is software (llvmpipe: 573 vs 163 ms/s at forced 60 fps). `select_renderer()` picks software for software GL, `SLINT_BACKEND` overrides. Software renderer needs the `software-renderer-path` feature or the `Path` icons vanish, and cannot transform items.
- **GUI cost model:** ~30 fps × full-window repaint; the dirty region is ~70% of the window because ScrollView content repaints as one unit. Reducing meter cadence is *not* an acceptable trade (looks choppy) — the user rejected it.
- **"Is anything listening" = PipeWire links, not stream state.** `node.passive` made the exported node stay `running` with no consumers, so the stream never left `Streaming` and the daemon filtered 24/7 with the output meter live. Consumers are now counted from `Link` globals (`link.output.node` == our node id) in the registry listener. Never re-add `node.passive`.
- **Recording is GUI-only.** The window captures both tracks itself with `pw-record` children (raw = physical mic node, filtered = `dfmic-source`), stopped with SIGINT so the WAV header is finalised. The daemon has no recording API; it just sees two more clients, which also means the output meter is live during a take with no special case.
- **Redraw trap (Slint 1.19):** any *animated* property that the render reads makes `global_instant` a render dependency; `update_animations` bumps it every event-loop iteration, so the window repaints at the display rate forever. The std ScrollView's scrollbar thumb (`animate width, height` in std-widgets) does exactly this: it doubled renders (62/s for 30 meter ticks, 16.9% CPU). `scrollbar-policy: always-off` → 10.5% CPU. Measure with `SLINT_DEBUG_PERFORMANCE=refresh_lazy,console` (prints "average frames per second") — it should never exceed the meter rate. Debug builds are a different story: at 32 fps they still burn ~62% of a core, ~50 of it in the unoptimised tick path (`DFMIC_PROBE=nometers` → 11.8%), so judge render changes by release numbers only.
